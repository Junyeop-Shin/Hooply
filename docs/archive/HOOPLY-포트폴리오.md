# HOOPLY — 농구 동호회 팀 배정 서비스

> 매주 참석자가 바뀌고 실력을 모르는 게스트가 섞이는 농구 모임에서, **균형 잡힌 팀을 추천하고 그 팀에 맞는 전술까지 알려 주는 모바일 웹 서비스**

- **서비스:** https://hooply-green.vercel.app (모바일 화면 기준 · 데모 계정은 아래 "직접 둘러보기")
- **코드:** https://github.com/Junyeop-Shin/Hooply
- **기간 · 인원:** 2026.09.09 ~ 2026.09.30 · 1인 (기획 · 설계 · 백엔드 · 프론트엔드 · 배포)
- **규모:** API 110개 · 화면 31개 · DB 마이그레이션 24개 · 자동 테스트 300여 개 (pytest 222 · Vitest 63 · Playwright E2E 22)

## 1. 어떤 문제를 푸는가

동호회 · 픽업 게임은 매주 12~16명이 모이고, 인원이 모자라면 실력을 모르는 게스트를 2~4명 부릅니다. 팀은 보통 "실력을 제일 잘 아는 사람이 정하기", "키 순서", "친한 사람끼리"로 나누는데, 그러면 이런 일이 생깁니다.

- 실력이 한쪽으로 쏠려 경기가 재미없다
- 볼 운반(1번) · 골밑(5번)을 맡을 사람이 한 팀에 몰린다
- 팀을 왜 이렇게 나눴는지 설명할 근거가 없어 불만이 쌓인다
- 기록이 남지 않아 다음 모임에도 똑같이 감으로 나눈다

## 2. 해결 방식

| 원칙 | 내용 |
| --- | --- |
| **추천은 알고리즘, 결정은 사람** | 실력 우선 · 친화도 우선 · 종합 **3가지 배정안**을 추천하고 매니저가 고르거나 고친다 |
| **아마추어의 현실 반영** | 1번 · 5번 자원을 먼저 나누고 실력 · 선호 포지션 · "같이 뛰고 싶은 사람"을 함께 최적화 |
| **최소 기록** | 개인 스탯 없이 **쿼터마다 뛴 5명과 점수만** 넣으면 실력 지표가 스스로 보정된다 |
| **설명 가능한 결과** | 배정 근거를 매니저에게는 수치로, 팀원에게는 문장으로. AI 는 그 문장만 쓴다 |

## 3. 주요 기능

**모임 운영 (매니저)**
- **자동 팀 배정 3안** — 같은 팀으로 묶기 · 갈라놓기 · 사전 배치 조건을 걸고 실행. 참석이 16명 이상이면 **3팀**(블랙 · 화이트 · 레드)으로도 나눌 수 있고, 18명이 넘으면 3팀을 권한다
- **배정안 수정** — 선수를 옮기거나 맞바꾸면 팀 지표가 바로 다시 계산된다
- **게스트** — 이름과 대략적인 등급만으로 등록, 다시 오면 기록이 이어지고 가입하면 본인이 확인해 기록을 가져간다
- **경기 기록** — 경기 후 쿼터별 점수와 뛴 5명을 한 화면에서 입력 (3팀이면 쿼터마다 뛴 두 팀 선택)
- **실력 근거** — 설문으로 잡은 처음 실력이 경기 기록을 거쳐 어떻게 바뀌었는지 선수별로 확인

**참여 (팀원)**
- 참석 응답 · 게스트 초대 · 확정된 배정 결과(다른 사람의 실력 점수는 보이지 않고 **자기 등급만**)
- **경기 후 투표** — "다음에 같이 뛰고 싶은 사람"을 우리 팀 · 상대 팀에서 2명씩 → 친화도 배정의 재료
- **기록 탭** — 활동일별 추세, 월간 코트 마진 순위, 행동 배지(동 · 은 · 금)

**AI 설명 · 전술 (LangChain + Gemini)**
- **AI 배정 설명**(매니저) · **AI 한마디**(팀원) — 팀 색깔, 활약이 기대되는 선수, 호흡이 좋을 조합, 내 역할
- **전술 추천** — 확정된 팀마다 22개 전술 중 맞는 3개와 **자리 배치**를 자동 추천, "AI 코치"가 이유를 설명
- **전술판** — 하프코트에서 단계별 재생, 상대 수비 5명이 전술이 가정한 방식(맨투맨/지역 × 스위치/스테이)대로 따라 움직인다
- **전술 편집기** — 팀원이 직접 움직임을 그리면 자리별 역할이 자동으로 붙고, AI 가 자리마다 할 일을 풀어 준다. 댓글 · 매니저 별표

**그 밖에** — 카카오 로그인 · 카카오톡 공유(초대 · 투표 독려 · 팀 구성 이미지), 새 가입자 시작 안내, 도움말, 관리자 콘솔(팀 승인 · 지표 보정)

## 4. 기술적으로 고민한 것

### ① 코트 마진을 그냥 쌓으면 실력이 아니다 → 기대 대비 잔차
쿼터 점수 차(코트 마진)를 그대로 누적하면 세 가지 이유로 실력과 멀어집니다 — 10명 합이 항상 0인 제로섬, 잘하는 사람이 약한 팀에 배정되는 역선택, **배정이 잘 될수록 점수 차가 사라지는 자기 파괴적 되먹임**. 그래서 "우리 팀과 상대 팀 실력으로 예상한 점수 차보다 얼마나 더 벌었는가(잔차)"를 쌓는 Elo 방식으로 실력을 갱신합니다(Adjusted Plus-Minus 계열).
- 참값을 아는 가상 동호회로 **시뮬레이션해 검증** — 앱 조건에서 실력과의 순위 상관이 원시 마진 0.61 → 잔차 모델 0.89, 팀 균형이 완벽한 극한에서도 0.24 → 0.49
- 데이터가 쌓이기 전에는 행동 기반 설문(12문항) + 매니저의 실력 순서 정렬을 사전값으로 쓰고, 등급은 **팀 안에서의 위치**(상위 10% A … 하위 10% E)로 보여 준다

### ② 배정 최적화 — 조건은 절대 깨지지 않게, 결과는 최적으로
- "같은 팀으로 묶기"를 벌점으로 처리하면 실력 우선 안에서 깨질 수 있어, **Union-Find 로 묶음을 한 덩어리(슈퍼노드)로 축약**해 탐색 단위 자체를 바꿨다 → 어떤 전략에서도 조건 위반이 원천적으로 불가능
- 2팀 · 18명(묶음 뒤)까지는 **완전 탐색으로 전역 최적 보장**(약 0.6초). 그 이상과 3팀은 **지역 탐색**(이웃 전체를 NumPy 로 한 번에 채점 + 흔들기, 21명 3팀 0.09초)
- 지역 탐색은 완전 탐색이 가능한 크기에서 **최적과 같은 답을 내는지 테스트 오라클로 검증** (3팀 15명 60/60, 2팀 16명 60/60)
- 실행 전에 조건이 가능한지 먼저 검사해, "누가 문제인지"를 담은 오류로 막는다

### ③ 케미는 측정하지 않고 선언받는다
두 사람의 "시너지"를 경기 기록으로 추정할 수 있는지 시뮬레이션해 보니, 현실적인 크기의 효과를 80% 검정력으로 잡으려면 둘이 함께 뛴 쿼터가 60~90개 — 주 1회 모임으로 3년 이상이 필요했습니다. 근거 없는 "케미 점수"는 감보다 나쁘다고 판단해, **경기 후 "다음에 같이 뛰고 싶은 사람" 투표**를 함께 참석한 횟수로 정규화해 친화도로 씁니다.

### ④ AI 는 판단하지 않고 설명만 — 그리고 효과를 데이터로 확인
- **판단은 규칙, 문장은 AI** — 누가 활약할지 · 어떤 전술 · 자리가 맞는지는 서버 규칙이 먼저 정하고, LLM 은 그 사실만 문장으로 바꾼다. 틀린 결정에 AI 의 권위를 씌우지 않기 위해서
- **가드레일** — 실명 대신 가명(P1 · 팀 A/B/D)만 보내고 되돌린다. 입력에 없는 사람 · 숫자가 나오거나 팀원용에 등급이 섞이면 버리고 규칙 설명으로 폴백. 결과 캐시 · 사용자당 요청 제한 · 예비 모델 재시도
- **검증 스크립트** — 배포 서버에 72건을 돌려 폴백 0 · 자동 점검 문제 0, 평균 응답 1.8~3.3초
- **AI 를 뺀 결정도 데이터로** — 전술 편집기에서 AI 가 역할까지 고르게 했더니 사람이 붙인 역할과의 일치율이 64%로 규칙(65%)과 같았고, 맞던 자리를 틀리게 바꾸기도 했다. 그래서 **AI 는 이유만 쓰게 바꾸고 규칙을 보강해 82%** 로 올렸다

### ⑤ 전술 엔진
- 전술을 좌표가 아니라 **동작의 순서**(이동 · 드리블 · 패스 · 스크린 · 컷 · 핸드오프 · 슛)로 저장하고, 재생 가능한지 서버에서 검사
- 역할 7종 × 설문 속성으로 선수별 역할 점수를 내고, 팀 · 전술마다 5자리 최적 배치를 **비트마스크 DP** 로 계산
- 상대 수비 움직임은 서버 · AI 없이 프론트 규칙 계산으로 시뮬레이션, requestAnimationFrame 보간으로 60fps (휴대폰 에뮬레이션 CPU 20배 저속에서도 59.6fps)

### ⑥ 운영 · 품질
- **쿼리 수 예산 테스트** — 자주 쓰는 API 가 쿼리를 몇 번 부르는지 상한을 두고 CI 에서 검사 (배정 실행 30 → 18회 등 최적화)
- **무료 인프라** — Neon(PostgreSQL) · Render(API) · Vercel(웹), 매일 DB 백업 · 매주 데모 데이터 자동 갱신 (GitHub Actions)
- **실사용 문제 대응** — iOS Safari 에서 반투명 하단 바 뒤 글자가 비치던 것, 배포 직후 열어 둔 탭에서 화면 조각 파일을 못 불러오던 것(자동 새로고침으로 복구) 등
- 보안 — bcrypt, JWT refresh 회전 · 폐기, 로그인 · AI 요청 제한, 비밀번호 재설정 토큰은 해시만 저장, 가입 여부를 드러내지 않는 응답

## 5. 기술 스택

| 영역 | 사용 기술 |
| --- | --- |
| Backend | Python 3.12 · **FastAPI** · SQLAlchemy 2.0 · Alembic · Pydantic v2 · NumPy |
| Database | **PostgreSQL** (운영 Neon, 로컬 Docker) |
| AI | **LangChain** · Google **Gemini** (구조화 출력 · 재시도 · 예비 모델) |
| Frontend | **React 19** · TypeScript · Vite · Tailwind CSS v4 · TanStack Query · Zustand |
| 인증 · 연동 | JWT · bcrypt · 카카오 로그인 / 카카오톡 공유 · Resend(메일) |
| 관리자 | SQLAdmin |
| 테스트 | pytest · Vitest · Testing Library · Playwright (모바일 Chromium) |
| 배포 · CI | Render · Vercel · Neon · Docker Compose · GitHub Actions (테스트 · DB 백업 · 데모 데이터 갱신) |

```
[모바일 브라우저] ── React SPA (Vercel)
        │ REST (JSON, JWT)
        ▼
   FastAPI (Render) ── 배정 엔진(NumPy) · 실력 갱신(잔차 Elo) · 전술 엔진
        │                    └─ LangChain → Gemini (가명 · 가드레일 · 캐시)
        ▼
   PostgreSQL (Neon)        SQLAdmin(/admin)
```
