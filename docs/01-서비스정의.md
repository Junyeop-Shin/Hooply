# HOOPLY — 서비스 정의

농구 동호회·픽업 게임의 **팀 나누기**를 데이터로 돕는 모바일 웹 서비스. 참가자의 실력·포지션·선호를 모아 균형 잡힌 팀 후보안을 추천하고, 경기 기록(쿼터 스코어)과 경기 후 투표를 쌓아 다음 배정을 더 정확하게 만든다.

## 1. 서비스 목적과 타겟 사용자

### 1.1 목적

1. 매 모임마다 반복되는 팀 구성 결정을 **알고리즘 추천 + 매니저 최종 결정**으로 바꿔 매니저의 부담을 줄인다.
2. 실력·포지션 균형이 맞는 팀을 만들어 참가자의 경기 만족도를 높인다.
3. 쿼터별 스코어와 출전자만 입력하는 **최소 기록**으로 개인 실력 지표를 누적해, 시간이 지날수록 배정이 정확해지는 데이터 루프를 만든다.

### 1.2 타겟 사용자

| 구분 | 대상 | 핵심 요구 |
| --- | --- | --- |
| 1차 | 동호회 매니저·총무 (20~45세, 주 1회 모임 운영) | 팀 나누기 시간 단축, 배정 근거 설명, 불만 응대 감소 |
| 2차 | 동호회 소속 참가자 (실력 편차 큰 아마추어) | 균형 잡힌 경기, 원하는 포지션, 납득되는 팀 구성 |
| 3차 | 여러 동호회를 운영·관리하는 관리자 | 팀 승인, 데이터 품질 관리, 이상치 보정 |
| 데이터 대상 | 게스트 (계정 없는 참가자) | 이름만으로 참석·배정·기록에 포함 |

이용 환경: 체육관에서 한 손으로 쓰는 **모바일 웹** 우선. 팀 코드·일정 링크는 카카오톡으로 공유. 기록은 경기 후 매니저가 입력.

## 2. 문제 정의

### 2.1 배경과 현황

- 동호회 모임은 매주 참석자가 바뀌고(12~14명), 인원이 부족하면 **게스트를 2~4명 부른다**. 게스트의 실력은 대부분 모른다.
- 팀은 "실력을 가장 잘 아는 사람이 정하기", "키 순서·가위바위보", "친한 사람끼리" 중 하나로 정해진다.
- 하루 동안 팀이 고정된 채 7~10쿼터를 뛰고, 6~7명 팀은 로테이션으로 쉰다. 다음 모임에는 처음부터 다시 짠다.

### 2.2 페인포인트와 원인

| # | 대상 | 문제 | 원인 |
| --- | --- | --- | --- |
| P1 | 매니저 | 매번 팀 구성에 시간·부담 | 참석자가 매주 바뀌어 매번 처음부터 설계 |
| P2 | 매니저 | 팀 구성 불만 응대 | 배정 근거가 매니저 머릿속에만 있음 |
| P3 | 매니저 | 근거를 설명하기 어려움 | 수치화된 실력·포지션 정보 없음 |
| P4 | 매니저 | 기록이 없어 다음 배정을 개선 못 함 | 개인 스탯 기록의 비용이 너무 큼 |
| P5 | 참가자·게스트 | 실력 불균형으로 재미없는 경기 | 객관적 실력 데이터 부재, 주관에 의존 |
| P6 | 참가자·게스트 | 핸들러(1번)·빅맨(5번)이 한쪽에 쏠림 | 희소 포지션 자원을 고려하지 않음 |
| P7 | 참가자 | 원하는 포지션으로 못 뛰는 경우 | 선호·가능 포지션 정보를 모음 |
| P8 | 참가자 | 원하지 않는 사람과 같은 팀 | 참가자 선호가 반영될 통로가 없음 |

### 2.3 핵심 난제 — 게스트 콜드 스타트

참석자가 고정된 리그와 달리 픽업 환경은 **데이터 없는 사람이 매번 섞인다.** 그래서 (a) 계정 없이도 참가자로 등록·누적할 수 있는 구조와 (b) 데이터가 없을 때 매니저 판단을 사전값으로 받는 장치가 서비스의 핵심 설계 요건이 된다.

## 3. 문제를 해결하는 기능

### 3.1 핵심 가치

1. **추천은 알고리즘, 결정은 사람** — 실력/친화도/종합 3가지 후보안 중 매니저가 고르거나 수정.
2. **아마추어 현실 반영** — 1번·5번 포지션을 먼저 확보한 뒤 실력·친화도·선호를 최적화.
3. **설명 가능한 결과** — 매니저에게는 수치, 플레이어에게는 문장으로 근거 제시.
4. **기록 부담 최소화** — 쿼터별 출전 5명과 스코어만 입력하면 코트 마진과 실력 지표가 자동 갱신.

### 3.2 기능 목록과 해결하는 문제

| ID | 기능 | 해결 | 구현 요약 |
| --- | --- | --- | --- |
| F1 | 온보딩 실력 설문 | P5, P7 | 12문항(행동 앵커·다중선택), 팀별 z-score로 사전 실력값 산출, 팀 가입 후 "동호회 내 내 위치" 1문항 |

설계서의 F17(로테이션 자동 제안)은 기록을 경기 후 입력하는 운영 방식과 맞지 않아 범위에서 제외했다.

### 3.3 왜 이 접근이 타당한가

- 12~14명 2팀은 조합이 2천 개 이하라 **완전 탐색으로 전역 최적을 보장**할 수 있다(휴리스틱 불필요).
- 원시 코트 마진은 제로섬·역선택 때문에 실력과 상관 0.43에서 정체하므로, **기대 마진 대비 잔차**를 누적한다(시뮬레이션 0.86).
- 코트 마진으로 케미를 측정하려면 페어당 60~90쿼터가 필요해 현실적으로 불가능하다. 케미는 **투표로 선언**받는다.
- 설문과 매니저 정렬은 첫 20회 모임까지 배정 품질을 좌우하므로 온보딩과 정렬 UI에 공을 들였다.

## 4. 액터와 요구사항

### 4.1 액터

| 액터 | 범위 | 부여 |
| --- | --- | --- |

## 5. 개요 ↔ 요구사항 ↔ 화면 일관성

문제(P) → 기능(F) → 요구사항(FR) → 화면(S) → API 의 추적 관계는 4.2절 표에 열로 두었다. 대표 흐름 두 개만 요약하면 다음과 같다.

- **P1 팀 구성 부담**: F4 일정·응답(S-09, S-10) → F13 게스트(S-11) → F14 정렬(S-19) → F5/F15 배정 실행(S-12) → F6/F7 결과·수정·확정(S-13, S-14). 매니저가 누르는 버튼 수로 보면 응답 확인 → 배정 실행 → 후보안 선택 → 확정 4단계다.
- **P4 기록 부재**: F8 쿼터 기록(S-15) → F10 잔차 갱신(서버) → F11 기록·지표(S-17, S-20, S-21) → 다음 회차 F5 배정 정확도 향상. F18 지난 기록 추가(S-22)로 도입 전 데이터도 같은 루프에 넣는다.

화면 ID와 화면별 요소·API 필드는 `02-UI흐름및화면설계.md`, 테이블은 `03-데이터모델.md`, API 전체는 `04-API명세.md` 와 `04-API명세-openapi.yaml` 에 있다.
