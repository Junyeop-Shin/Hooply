# HOOPLY — UI 흐름 및 화면 설계

구현된 화면(React Router 경로) 기준이다. 각 화면의 UI 요소·데이터 필드·호출 API·논리 흐름을 적고, 마지막에 사용자 흐름과 예외 시나리오를 정리한다. 필드 이름은 API 응답 스키마(`04-API명세-openapi.yaml`)와 동일하다.

## 1. 설계 원칙

1. 모바일 우선, 한 손 조작. 화면당 주요 액션 하나(오렌지 버튼)를 하단에 고정.
2. 역할별 진입점 분리. 같은 화면도 매니저/플레이어에 따라 카드가 다르다.
3. 화면 요소 = API 필드. 화면의 모든 값은 응답 필드에 1:1 대응한다.
4. 남의 실력은 매니저에게만. 수치는 물론 등급도 플레이어 화면에는 나오지 않는다. **내 등급만 나에게 보인다**(S-17) — 등급이 남에게 보이면 수치를 가린 의미가 없다.
5. 뒤로 가기는 브라우저 히스토리를 따른다. 새로고침·딥링크처럼 히스토리가 없을 때만 기본 경로로. **흐름이 끝나는 동작**(배정 확정 · "확정된 결과 보기" · 일정 수정 저장 · 전술 고치기 저장 · 지우기 · 본인 매니저 해제)은 결과 화면으로 새로 이동하지 않고 거쳐 온 화면만큼 히스토리를 **되감아** 상위 화면으로 간다(`useFinish`, `components/layout.tsx`) — 그래서 뒤로가 조건 설정 · 수정 화면으로 되돌아가거나 같은 화면이 두 번 나오지 않는다(확정 뒤 일정 화면에서 뒤로 = 팀 화면). 되감을 히스토리가 없으면 경로로 바꿔치기한다. 투표의 "일정으로 돌아가기", 팀 가입 직후의 내 위치 저장, 못 여는 팀(403 · 404) → 홈도 바꿔치기다.
6. 기기가 어두운 화면 모드면 자동으로 따라간다 (아래 1.1).
7. 한 개념에는 한 단어만 쓴다 (아래 1.2).

### 1.1 색 — 밝은 화면 / 어두운 화면

브랜드 원색은 **코트 오렌지 + 짙은 남색** 두 가지이고 값이 고정이다. 그 위에 `canvas`(바탕)·`surface`(카드)·`ink`(글자)·`line`(테두리)처럼 **역할로 이름 붙인 색**을 얹고, 화면 코드는 역할 이름만 쓴다. 기기가 어두운 화면 모드일 때는 `prefers-color-scheme` 미디어 쿼리에서 이 역할 색의 값만 바꾼다 (`frontend/src/index.css`). 화면마다 모드를 분기하는 코드는 없다.

- **어두운 화면의 바탕은 회색이 아니라 짙은 남색 계열**이다. 밝은 화면에서 헤더가 쓰던 색이 그대로 바탕이 되므로 모드가 바뀌어도 같은 서비스로 보인다.
- 오렌지는 어두운 바탕에서 조금 밝게 올리고, 그 위 글자는 흰색 대신 진한 갈색을 써서 대비를 확보한다 (`--color-on-brand`).
- 밝은 화면의 채운 버튼 바탕(`--color-brand`)은 원색(`#f26b1d`, 흰 글자와 3.05:1)보다 한 단계 짙은 `#c24e0e` 를 쓴다 — 흰 글자 4.78:1 로 WCAG AA(4.5:1)를 맞춘다. 오렌지 글자 · 링크(`--color-brand-ink`)도 `#b3430c` 로 짙게.
- **블랙 팀 / 화이트 팀 칸은 모드와 무관하게 고정**이다. 유니폼 색이라 뒤집으면 뜻이 달라진다. 화이트 팀 칸은 어두운 모드에서 한 단계만 낮춰 눈부심을 줄이고, 그 안의 체크박스도 밝은 모드로 그린다(`[color-scheme:light]`).
- 별도의 모드 전환 버튼은 두지 않는다. 기기 설정을 따른다.

### 1.2 용어

한 개념을 여러 단어로 부르지 않는다. 통계·개발 용어는 화면에 내지 않는다.

| 개념 | 쓰는 말 | 쓰지 않는 말 |
| --- | --- | --- |
| 모이는 날 하나 | **일정** (순서를 셀 때만 "회차") | 모임, 활동 |
| 팀에 속한 사람 | **팀원** | 회원, 선수, 플레이어 |
| 계정 없이 온 사람 | **게스트** | 손님, 비회원 |
| 그날 오기로 한 사람 | **참석자** | 참가자 |
| 팀을 나누는 일 | **팀 배정**, 결과 하나는 **배정안** | 편성, 후보안, 팀 짜기, 실행 |
| 경기 기록 화면 | **경기 기록** | 쿼터 기록 |
| 실력 표시 | 모두에게 **실력 등급**(A~E), 매니저에게 **실력 점수** | 지표, 티어, 실력값, 종합 실력 |
| 실력의 근거 | **시작 점수**, **기여 점수**, **점수 차**, **정보 충분도**, **세부 능력** | 사전값, 잔차, 코트 마진, 신뢰도, 6축 |
| 참석 여부 | **참석 응답** | RSVP |
| 경기 후 평가 | **투표** | 피어 설문, 응답 |
| 배정 조건 | **묶기 / 갈라놓기 / 미리 배치** | 제약, LOCK/SEPARATE/PIN |

문체는 화면·서버 메시지 모두 **해요체**로 통일한다. 보조용언은 띄어 쓴다("골라 주세요"). 서버가 주는 오류 문구도 그대로 화면에 뜨므로 같은 규칙을 지키고, 컬럼명·HTTP 메서드·환경 변수 이름·내부 id 는 담지 않는다.

### 1.3 알림 · 확인 · 기다림 · 불러오기 실패

- **브라우저 기본 `alert()` / `confirm()` 은 쓰지 않는다.** 카카오톡 인앱 브라우저에서 모양이 제각각이고 접근성 이름도 없다. 결과 알림은 아래쪽에 잠깐 뜨는 **토스트**, 지우기 · 확정처럼 되묻는 일은 아래에서 올라오는 **확인 시트**(제목 · 설명 · 확인/취소, 되돌릴 수 없는 일은 붉은 버튼)로 한다 (`store/feedback.ts`, `components/toast.tsx` · `confirm-sheet.tsx`). 화면이 오류를 따로 보여 주지 않는 변경 요청이 실패하면 서버 문구를 토스트로 띄운다
- **기다림은 두 층이다** (`components/loading.tsx`, `store/loading.ts`, `Spinner` 의 `page`): **화면 전체**가 비어 있는 로딩(`<Spinner page />`)은 0.15초 뒤 화면을 살짝 흐리게 덮고 가운데에 링 **하나만** 그린다 — 금방 끝나는 로딩에서는 번쩍이지 않고, 터치는 막지 않는다. **섹션 하나**만 불러올 때(`<Spinner />`)는 그 자리에 작은 링만 그리고 문구도 덮개도 없다 — 이미 보이는 내용이 흐려지지 않게. 어느 쪽이든 **5초를 넘기면** 전체 덮개 하나로 넘겨받아(섹션 링은 숨는다) 농구 문구("코트 바닥 닦는 중…" 등 5개 중 무작위, 6초마다 바뀜)와 "처음 접속하면 최대 1분쯤 걸려요"를 띄운다 — 무료 서버가 잠에서 깨는 데 30~60초 걸린다 (`lib/wait-messages.ts`). 덮개는 TopBar 위, 안내 팝업 · 시트 · 토스트 아래(z-20)이고, 시트나 팝업이 열려 있는 동안은 흐림 없이 링과 문구만 둔다. 요청은 70초가 지나면 끊고 "서버 응답이 너무 늦어요. 잠시 뒤 다시 시도해 주세요."를 보여 준다. 불러오기가 실패하면 링을 계속 돌리지 않고 아래의 `LoadError` 로 바꾼다
- **불러오기 실패는 빈 화면과 구분한다.** "일정이 없어요" 같은 빈 상태 대신 오류 문구와 **다시 시도** 버튼을 보여 준다 (`LoadError`)
- **하단 시트**는 열려 있는 동안 포커스가 시트 안에서만 돌고 뒤 화면이 스크롤되지 않으며, 닫으면 연 버튼으로 포커스가 돌아간다. 탭 묶음은 `tablist` / `tab` 역할을 붙인다. 누르는 칸은 보이는 모양이 작아도 44px 이상
- **탭 사이 로그인 맞추기:** 다른 탭이 토큰을 갱신(회전)하거나 로그아웃하면 이 탭도 저장소의 값을 따라간다 — 이미 버려진 refresh 토큰으로 요청하다 로그아웃되지 않게

## 3. 화면별 요소 · 데이터 · API · 흐름

### S-01 로그인
- **UI 요소:** HOOPLY 로고·문구, 카카오로 시작하기(노란 버튼), 이메일·비밀번호 입력, 로그인 버튼, 비밀번호 찾기 링크(S-31), 회원가입 링크
- **데이터 필드:** `email`, `password` → 응답 `access_token`, `refresh_token`
- **API:** `POST /auth/login`, `GET /auth/kakao/login-url?redirect_uri=` (카카오 버튼)
- **흐름:** 성공 → 홈. 카카오 버튼은 인가 URL로 이동(state를 sessionStorage에 보관). 401 → "이메일 또는 비밀번호가 올바르지 않아요."

### S-02 회원가입
- **UI:** 이메일, 비밀번호(8자 이상), 이름, 닉네임(선택), 키(cm), 가입하기 버튼. 안내 문구 "가입하면 홈에서 시작 안내가 떠요. 팀 가입과 2분짜리 실력 설문을 차례로 도와드려요."
- **필드:** `SignupRequest{email, password, name, nickname?, height_cm?}` → `TokenPair`
- **API:** `POST /auth/signup`
- **흐름:** 성공 → 홈(S-04, 시작 안내 팝업 S-27이 설문 · 팀 가입으로 안내). `409 EMAIL_DUPLICATED` → 필드 오류 표시.

### S-03 온보딩 설문
- **UI:** 진행률, 문항 카드(단일선택은 자동 다음, 다중선택 칩, 5단계 서열, 키 스테퍼), 이전/다음, 제출
- **필드:** `SurveyTemplate{id, questions[]{id, code, answer_type, options[]}}` → `SurveyResponseIn{template_id, answers[]{question_id, option_ids[] | numeric_value}}` → `MyProfile`
- **API:** `GET /surveys/onboarding`, `POST /surveys/onboarding/responses`
- **흐름:** 제출 → 팀 코드가 있으면 S-06, 없으면 홈. 재제출은 `409 ALREADY_SUBMITTED`. 답하던 단계와 답은 이 탭(sessionStorage, `survey-draft-<템플릿 id>`)에 보관해 새로고침하거나 잠깐 다른 화면에 다녀와도 이어서 하고, 제출하면 지운다. 로그인 · 로그아웃 때는 설문 · 쿼터 · 배정 조건 · 전술 초안을 모두 지워 다른 계정의 입력이 다음 사람에게 이어지지 않게 한다(`lib/drafts.ts`, 토큰 갱신에는 지우지 않는다).

### S-04 홈
- **UI:** 인사말, 다음 모임 카드(D-day·일시·내 응답 상태), 게스트 기록 확인 카드(같은 이름의 미병합 게스트가 있을 때), 다가오는 일정 목록, 내 팀 목록(기본 팀 배지, 기본 팀이 아닌 팀은 카드 **아래 바깥**에 "<팀 이름> 기본 팀으로 설정하기" — 카드 안에 두면 팀을 열려다 기본 팀이 바뀐다), 팀 코드로 가입·팀 만들기 버튼, 하단 탭(홈/프로필)
- **필드:** `UserDetail{name, nickname, onboarding_completed, primary_team_id}`, `TeamMembershipView{team_id, team_name, team_status, approval_status, role, member_count}`, `EventView{event_date, start_time, venue, my_attendance, attend_count}`
- **API:** `GET /me`, `GET /me/teams`, `GET /teams/{id}/events?size=50` (팀별), `PATCH /me{primary_team_id}`
- **흐름:** 설문 미완료면 설문 유도 카드가 먼저. 일정 카드 탭 → S-10. 팀 카드 탭 → S-07. 일정이나 내 팀을 못 받았으면 "팀이 없어요 → 만들기" 대신 오류와 다시 시도를 보여 준다(이미 팀이 있는 사람이 팀을 또 만들지 않게).

### S-05 팀 생성
- **UI:** 팀 이름, 소개, 홈 코트, 발급 버튼 → 완료 화면(팀 코드, 복사, 카카오톡 공유, 승인 대기 안내)
- **필드:** `TeamCreate{name, description?, home_court?}` → `TeamCreated{id, team_code}`
- **API:** `POST /teams`
- **흐름:** 생성 → 승인 대기(관리자 콘솔) → 5명 이상 → 활성. 공유 문구에 초대 링크 `/teams/join?code=`.

### S-06 팀 가입
- **UI:** 8자리 코드 입력(초대 링크면 미리 채움), 가입 버튼
- **필드:** `{team_code}` → `TeamDetail`

### S-13 배정 결과 (MANAGER)
- **3팀 (v1.7):** 팀 카드 세 개를 한 줄에(좁은 카드 — 포지션·표시 한 글자, 작은 등급 원). 한 명을 고르면 "← 블랙으로 옮기기 · 레드로 옮기기 →"처럼 그 팀 쪽을 가리키는 버튼이 팀마다, 두 팀에서 고르면 맞교체. 세 번째 팀에서 또 고르면 새로 고른다. 예상 실력 차는 "가장 강한 팀과 가장 약한 팀" 기준
- **UI:** 전략 3탭(실력/친화도/종합), 예상 실력 차·균형 점수와 설명 문구, 수동 수정 표시·초기화, 팀 카드 2개(포지션·이름·묶음/고정/분리 태그·등급), 선수 탭 → 옮기기/맞교체 버튼, **"AI 배정 설명" 카드**(규칙 설명 대신), 포지션 슬롯 표, 확정 버튼
- **필드:** `AssignmentRunView{candidates[]{id, strategy, total_score, metrics{skill_spread, manually_edited, original_squads}, explanation, is_adopted, squads[]{squad_no, squad_name, avg_skill, avg_height_cm, members[], assigned_positions, manual_override_ids}}, constraints, warnings}`
- **API:** `GET /assignments/runs/{id}`, `PATCH /assignments/candidates/{id}` (`exchanges`/`moves`), `POST …:reset`, `POST …:adopt`, `POST /assignments/candidates/{id}/ai-explanation`
- **AI 배정 설명 (docs/07 FR-51):** 규칙 설명("이렇게 나눈 이유") 카드를 대신한다. 화면에 들어오면 바로 부르고, 결과를 타자 치듯 보여 준다 — 두 팀 색깔 요약 · 활약이 기대돼요 · 호흡이 좋을 조합 · 부족한 역할 · 경기 중 확인할 점. 선수를 옮기면 1.2초 뒤 새로 부른다. 한 번 끝까지 본 설명은 다시 타자 치지 않고, 되돌려 전에 받은 구성이 되면 받아 둔 설명을 바로 보여 준다. AI 가 실패하면 같은 자리에 규칙 설명이 "AI" 표시 없이 나온다
- **흐름:** 묶음은 통째로 이동, 갈라놓은 쌍은 팀 맞바꾸기만. `422 INVALID_SWAP` 사유 표시. 확정 → S-14 (일정 → 배정 실행 → 이 화면을 되감아 일정 화면으로 가므로 뒤로는 팀 화면. 받아 둔 AI 코치 · 전술 자리 배치 캐시도 그때 비운다). 같은 일정의 확정이 동시에 들어오면 하나만 되고 나머지는 `409`. 쿼터 기록이 생긴 뒤에는 수정 · 초기화 · 확정이 `422 ASSIGNMENT_LOCKED`.
- **실행 기록:** 한 회차에 남는 배정은 하나다. 확정하지 않고 흘려보낸 실행은 다시 실행할 때 지우고, 확정하는 순간 그 회차의 지난 실행도 지운다. 재배정을 돌려 보는 동안에는 직전 확정안이 그대로 공개되어 있다.

### S-14 배정 확정 결과
- **v1.4:** 따로 가는 화면이 아니라 **배정이 확정된 일정 화면(S-10) 자체가 결과**다(`/events/:id/assignment` 는 `/events/:id` 로 넘긴다). 순서: 팀 배정 결과(내 팀 · AI 설명 · 두 팀 명단) → 매니저 재배정 → **이 팀에 맞는 전술**(팀원은 내 팀만, 매니저는 모든 팀, 전술마다 "막히면" 대안) → 매니저만 접힌 **참석 현황 · 관리**. 팀원에게는 참석 현황(누가 불참했는지)과 카카오톡 공유를 보여 주지 않는다
- **UI:** 내 팀·배정 포지션 헤더, **매니저: "AI 배정 설명" · 팀원: "AI 한마디" 카드**(규칙 설명 대신), 팀 블랙 / 팀 화이트 카드(내 이름 강조), 카카오톡 공유(매니저만), 재배정(매니저, 종료 전 — 쿼터 기록이 있으면 버튼 대신 "경기 기록이 있는 일정은 팀을 다시 짤 수 없어요. 쿼터 기록을 먼저 지워 주세요."), **이 팀에 맞는 전술**(아래 · 상대 수비 토글), 접힌 참석 현황 · 관리(매니저)
- **필드:** `AdoptedAssignment{strategy, explanation, squads[], my_squad_no, my_player_id, my_assigned_position, total_score}` — 플레이어 응답은 `avg_skill`, `skill_grade` 가 null
- **3팀:** 팀 카드 세 개를 한 줄에, 카카오톡 공유 이미지도 세 팀. 매니저는 모든 팀의 전술을 본다
- **이 팀에 맞는 전술 (docs/07 FR-45 · 52):** 제목 오른쪽 상대 수비 두 칸 토글(맨투맨 수비 ↔ 지역 수비, 누를 때마다 바뀜, 기본 맨투맨). 팀마다 적합도 75 이상인 전술 중 상위 3개가 **자동으로** 뜨고(매니저가 고르지 않음) 카드는 접힌 채 시작한다. 팀마다 위에 **"AI 코치" 한 줄 요약**. 카드를 펼치면 **전술 설명 한 섹션**(AI 이유 · 핵심 자리 · 주의할 점 · 막히면) → 자리("① 볼 핸들러 허재", 이름 아래 줄에 "예비 양동근 · 김승현" — 같은 전술판 5명 중 그 역할도 맞는 사람) → "전술판에서 보기". 매니저에게는 "선수별 근거 보기"(자리별 점수 · 충족 속성 · 부족한 점 · 벤치 교체 후보). 기준을 넘는 전술이 없으면 "오늘 팀 구성으로는 적합도 75를 넘는 전술이 없어요". 그 팀의 하프코트 팀 전술도 후보다

### S-15 쿼터 기록
- **3팀 (v1.7):** 쿼터 카드 위에 작게 **대진**(첫째 팀 ▾ vs 둘째 팀 ▾). 고른 두 팀이 그 쿼터의 두 칸이 되어 득점 칸 이름·색·출전 명단이 그 팀을 따른다. 한 칸의 팀을 바꾸면 그 칸 출전은 새 팀 앞 5명으로, 이미 다른 칸에 있는 팀을 고르면 두 칸을 맞바꾼다. "새 멤버 추가"도 세 팀 버튼. 상단 총점은 숨기고, 플레이어 결과는 팀별 표(쿼터 · 득 : 실 · 승 · 패)와 쿼터마다 "화이트 6 : 9 레드", 출전 쿼터 수는 팀별 세 칸. 로테이션 제안은 없다
- **UI (매니저):** 쿼터 카드 세로 누적 — 스코어 −/+ 및 두 자리 키패드(팀당 0~99점), 쿼터 길이(**기본 8분**, 1~10분 중에서 고름), 팀별 출전 5명 체크(그 팀 사람 → 아래 "다른 팀 · 옮겼으면 여기서 체크"), 삭제(점수나 명단을 넣은 쿼터면 확인 시트로 한 번 묻는다), 카드 맨 아래 "＋ 새 멤버 추가"(늦게 온 회원 · 당일 게스트를 이름 검색으로 팀 명단에 넣고, 처음 온 게스트는 이름만으로 등록 · 참석 처리). 쿼터 추가(직전 라인업 복사), 출전 인원 경고, 출전 쿼터 수, 일괄 저장. 임시 저장 복원 배너 — 저장하지 않고 나갔다 오면, 그사이 서버 기록이 바뀌지 않았을 때만 고치던 내용을 되살린다. 입력하는 도중에 서버 기록이 달라지면(다른 기기에서 저장): 아직 아무것도 안 고쳤으면 조용히 새 기록으로 바꿔 끼우고, 고치고 있었으면 "다른 기기에서 기록이 바뀌었어요" 경고와 **다시 불러오기** 버튼을 보여 주고 저장을 막는다 — 일괄 저장은 전체 교체라 그대로 저장하면 다른 기기의 기록을 덮어쓰기 때문이다(`lib/quarter-draft.ts` `draftMatchesServer`). 저장된 쿼터를 불러오지 못했으면 입력 화면을 만들지 않고 오류와 다시 시도만 보여 준다 — 일괄 저장은 전체 교체라 빈 초안을 저장하면 서버 쿼터가 지워지기 때문이다(저장 버튼도 불러오기에 성공했을 때만 켜진다)
- **UI (플레이어):** 총점 보드(3팀이면 팀별 표), 쿼터별 스코어·라인업, 출전 쿼터 수

### S-30 전술 편집기
- **v1.7:** 팀원 누구나 만든다(고치기 · 지우기는 만든 사람 · 매니저, 아니면 "만든 사람이나 매니저만 고칠 수 있어요"). "대상 수비" 대신 **상대 수비(맨투맨 · 지역 2-3) · 스크린 대응(스위치 · 스테이)** — 이 전술이 가정한 수비로 미리 보기와 전술판이 움직이고, 추천도 이 수비 상대로만. 마지막 단계를 이동으로 끝내도 된다
- **UI:** 이름 · 한 줄 설명(선택) · 상대 수비(맨투맨 · 지역 2-3) · 스크린 대응(스위치 · 스테이) · 상황(하프코트 · 인바운드) → "움직임 그리기"(제목 오른쪽 "↶ 되돌리기"(바로 앞 변경, 50번까지) · "처음으로"(연 때의 움직임)): 단계 탭(시작 위치 · 1단계 · … · + 단계), 안내 한 줄, 편집 코트, (시작 위치) 처음 공 칩 1~5 / (단계) 동작 칩 · 동작 목록(×) · 단계 설명(비우면 자동) · 단계 지우기, 검사 경고("이대로는 재생할 수 없어요" + 단계별 이유) → 미리 보기(전술판 그대로, 수비 시뮬레이션 포함) → 자리별 역할(선택 상자 + 이유 한 줄, 제목 오른쪽 "AI로 이유 설명 받기" — 역할은 그대로 두고 이유만 AI 문장으로) → 막히면(①~⑤ 칩으로 자리 넣기, 보이는 모습) → (고치기) 전술 지우기. 하단 저장 버튼은 이름과 재생 가능한 움직임이 있어야 켜진다
- **조작:** 시작 위치에서는 동그라미를 끌어 옮긴다. 단계에서는 동그라미를 누르면 그 사람에게 가능한 동작 칩(공 가진 사람: 드리블 · 패스 · 핸드오프 · 슛, 아니면: 이동 · 컷 · 스크린)이 뜨고, 패스·핸드오프는 받을 사람을, 이동·컷·드리블은 코트를, 스크린은 동료 → 설 자리 순서로 누른다. 한 사람 · 공 동작은 한 단계에 하나라 겹치면 새 것으로 바뀐다
- **필드:** `TeamPlayIn{name, summary, defense, situation, counter, start[5], ball, steps[], roles?, role_source}`, `PlayCheck{playable, errors[], roles[], reasons[]}`, `RoleSuggestion{roles[](보낸 그대로), reasons[], source, fallback}`
- **API:** `POST /teams/{id}/plays:check`(0.4초 멈춘 뒤), `POST /teams/{id}/plays:ai-roles`, `POST /teams/{id}/plays`, `GET/PUT/DELETE /teams/{id}/plays/{play_id}`
- **흐름:** 저장 → 그 전술의 전술판(S-29). 고치기 저장은 전술판으로, 지우기는 팀 화면으로 히스토리를 되감는다(1장 원칙 5). 저장하지 않은 입력(움직임 · 이름 · 설명 · 막히면 · 상대 수비 · 역할)이 있으면 뒤로 가기에서 "저장하지 않고 나갈까요?" 확인 시트, 새로고침 · 탭 닫기에서는 브라우저가 한 번 묻는다. 편집 중 내용은 이 탭(sessionStorage, `play-draft-<사용자 id>-<팀 id>-<전술 id|new>`)에 0.3초 멈출 때마다 보관해, 뒤로 가기 · 제스처 · 새로고침으로 나갔다 돌아오면 이어서 할지 묻는다(서버 전술이 더 새것이거나 연 때의 내용과 같으면 묻지 않고 버린다). 저장 · 지우기 때 지운다(`lib/play-draft.ts`). 역할은 규칙 → 직접 순서로 마지막 것이 남고, AI 는 역할을 바꾸지 않고 이유만 쓴다(docs/07 D19 · D23). 움직임이나 역할을 바꾸면 받은 AI 설명은 사라진다. 역할을 바꿔 저장하면 일정마다 저장해 둔 그 전술의 자리 배치가 지워진다

### S-27 시작 안내 (튜토리얼)
- **목표:** 처음 쓰는 사람이 팀에 들어가 첫 경기를 준비하게 돕되, 억지로 따라가게 하지 않는다. 가짜 화면은 만들지 않는다
- **① 시작 팝업 (한 번):** 새 가입자가 홈에 처음 오면 "처음이시죠?" 팝업. **안내 받기** / **혼자 둘러볼게요**. 거절하면 체크리스트도 기능별 첫 안내도 뜨지 않는다. 가입 직후 설문으로 바로 보내던 것은 홈으로 바꿨다
- **② 홈 체크리스트:** 경로를 먼저 고른다("팀 코드를 받으셨나요?"). 며칠 안에 끝나는 준비 4단계만 담는다

  | | 팀원 | 매니저 |
  | --- | --- | --- |
  | 1 | 팀 코드로 가입 | 팀 만들기 |
  | 2 | 실력·포지션 설문 | 실력·포지션 설문 |
  | 3 | 이 동호회에서 내 실력 위치 | 팀원 초대 (팀 활성화까지 · 승인 상태와 n/5명) |
  | 4 | 첫 일정에 참석 응답 (본인 응답만) | 첫 일정 등록 |

  단계는 **서버가 실제 데이터로 판정**한다(`GET /me/tutorial`). 다른 사람의 행동이 먼저 필요한 단계는 숨기지 않고 **대기 중** + 이유("매니저가 일정을 올리면 여기서 바로 응답할 수 있어요", "팀이 활성화되면 열려요")로 보여 주고, 조건이 채워지면 저절로 누를 수 있게 바뀐다. 팀 만들기 · 팀 가입 · 일정 등록 · 내 위치 저장을 마치면 체크리스트를 바로 다시 받아 그 단계가 곧장 끝난 것으로 보인다. 못 받았으면 빙글빙글 대신 오류와 다시 시도를 보여 준다. × 로 닫으면 끝. 다 마치면 "앞으로 이런 순서로 진행돼요" 흐름표를 한 번 보여 주고 사라진다. 체크리스트가 떠 있는 동안 홈의 "설문 아직" 카드는 숨긴다
- **②-1 스포트라이트:** 안내 중에는 지금 할 칸만 밝게 두고 나머지 화면을 어둡게 덮는다(칸에 주황 테두리 + 짧은 말풍선). 홈에서는 경로 선택 칸 → 다음 할 일 칸을 한 번씩 밝히고(같은 단계는 한 번만, 기기에 기억), 단계 버튼을 눌러 들어간 화면에서는 그 화면의 할 칸을 밝힌다 — 팀 코드 입력칸과 가입하기 · 팀 이름과 팀 코드 발급받기 · 팀 코드 공유 칸 · 참석/불참 버튼 · 날짜와 등록 버튼. 설문과 내 위치 문항은 화면 전체가 그 일이라 밝히지 않는다. 덮개는 누르는 것을 막지 않고, 밝은 칸을 누르거나 "알겠어요"·Esc 로 사라진다. 대상 칸은 `data-tutorial="<단계 키>"` 로 표시하고 말풍선 문장은 `tutorial-content.ts` 의 `SPOTLIGHT`
- **③ 기능별 첫 안내:** 배정·경기 기록·투표·배정 결과·기록 탭은 경기가 있어야 열려서 체크리스트에 넣지 않는다. 대신 그 화면에 **처음 들어갔을 때** 맨 위에 닫을 수 있는 안내 한 장(전술 탭 포함)(도움말 해당 주제 링크 + "알겠어요"). 닫은 안내는 다시 뜨지 않는다
- **상태:** `users.tutorial_state`(PENDING · ACTIVE · CLOSED · DONE · DECLINED) · `tutorial_path` · `tutorial_tips_seen`. 기능 도입 전 가입자는 DECLINED — 아무것도 뜨지 않는다. 도움말 맨 위 "시작 안내 다시 보기"로 누구나 다시 켤 수 있다(경로 선택부터)
- **문장:** `frontend/src/lib/tutorial-content.ts` (첫 안내 · 흐름표), 단계 문구는 `backend/app/services/tutorial_service.py`

### S-31 비밀번호 찾기 · 재설정
- **UI:** (찾기) 이메일 입력 → "메일을 보냈어요" 안내(가입 여부와 관계없이 같은 안내). (재설정) 메일 링크로 열면 새 비밀번호 · 확인(8자 이상, 서로 다르면 인라인 오류) → 완료 후 로그인
- **필드:** `ForgotPasswordRequest{email}`, `ResetPasswordRequest{token, new_password}`
- **API:** `POST /auth/password/forgot`(항상 202, 요청 제한), `POST /auth/password/reset`(`400 TOKEN_INVALID_OR_EXPIRED`)
- **흐름:** 토큰은 30분 · 1회용이고 DB 에는 해시만 둔다. 메일은 Resend 로 보낸다(키가 없으면 서버 로그). 카카오 전용 계정도 재설정하면 이메일 로그인이 더해진다. 재설정하면 모든 기기의 로그인이 끊긴다.

## 4. 사용자 흐름

**흐름 A — 신규 플레이어 온보딩**
S-01 → (카카오 또는 S-02 가입) → S-03 설문 → 팀 코드 있음? 예: S-06 → S-23 내 위치 → S-07 / 아니오: S-05 팀 생성 → 코드 공유 → 관리자 승인 대기

**흐름 B — 모임 운영 (매니저)**
S-09 일정 등록 → (응답 수집, 게스트 초대 S-11) → S-10 참석 현황 → (필요 시 응답 미리 마감) → S-12 배정 실행(제약 설정) → S-13 후보안 비교·수정 → 확정(S-14 공개) → 일정 시작 후 S-15 쿼터 기록 → 일정 종료 후 S-10에서 투표 독려 공유

**흐름 C — 참여 (플레이어)**
S-04 홈 다음 모임 카드 → S-10 참석 응답 → (확정 후) S-14 결과 → 일정 종료 후 S-07 투표 배너 → S-16 투표 → S-17 기록 확인

**흐름 D — 게스트가 회원이 된 경우**
게스트로 S-11 등록·기록 누적 → 본인이 S-02/카카오 가입 + S-06 팀 가입 → 홈(S-04)·팀(S-07)에 "이전 모임 기록이 있어요. 본인이 맞나요?" 카드 → **내 기록이에요**(병합) / **아니에요**(다시 묻지 않음). 이름이 다르면 S-08 "기록 이어받기 제안"으로 매니저가 병합
