# HOOPLY — UI 흐름 및 화면 설계

구현된 화면(React Router 경로) 기준이다. 각 화면의 UI 요소·데이터 필드·호출 API·논리 흐름을 적고, 마지막에 사용자 흐름과 예외 시나리오를 정리한다. 필드 이름은 API 응답 스키마(`04-API명세-openapi.yaml`)와 동일하다.

## 1. 설계 원칙

1. 모바일 우선, 한 손 조작. 화면당 주요 액션 하나(오렌지 버튼)를 하단에 고정.
2. 역할별 진입점 분리. 같은 화면도 매니저/플레이어에 따라 카드가 다르다.
3. 화면 요소 = API 필드. 화면의 모든 값은 응답 필드에 1:1 대응한다.
4. 남의 실력은 매니저에게만. 수치는 물론 등급도 플레이어 화면에는 나오지 않는다. **내 등급만 나에게 보인다**(S-17) — 등급이 남에게 보이면 수치를 가린 의미가 없다.
5. 뒤로 가기는 브라우저 히스토리를 따른다. 새로고침·딥링크처럼 히스토리가 없을 때만 기본 경로로.
6. 기기가 어두운 화면 모드면 자동으로 따라간다 (아래 1.1).
7. 한 개념에는 한 단어만 쓴다 (아래 1.2).

### 1.1 색 — 밝은 화면 / 어두운 화면

브랜드 원색은 **코트 오렌지 + 짙은 남색** 두 가지이고 값이 고정이다. 그 위에 `canvas`(바탕)·`surface`(카드)·`ink`(글자)·`line`(테두리)처럼 **역할로 이름 붙인 색**을 얹고, 화면 코드는 역할 이름만 쓴다. 기기가 어두운 화면 모드일 때는 `prefers-color-scheme` 미디어 쿼리에서 이 역할 색의 값만 바꾼다 (`frontend/src/index.css`). 화면마다 모드를 분기하는 코드는 없다.

- **어두운 화면의 바탕은 회색이 아니라 짙은 남색 계열**이다. 밝은 화면에서 헤더가 쓰던 색이 그대로 바탕이 되므로 모드가 바뀌어도 같은 서비스로 보인다.
- 오렌지는 어두운 바탕에서 조금 밝게 올리고, 그 위 글자는 흰색 대신 진한 갈색을 써서 대비를 확보한다 (`--color-on-brand`).
- **블랙 팀 / 화이트 팀 칸은 모드와 무관하게 고정**이다. 유니폼 색이라 뒤집으면 뜻이 달라진다. 화이트 팀 칸은 어두운 모드에서 한 단계만 낮춰 눈부심을 줄이고, 그 안의 체크박스도 밝은 모드로 그린다(`[color-scheme:light]`).
- 별도의 모드 전환 버튼은 두지 않는다. 기기 설정을 따른다.

### 1.2 용어

한 개념을 여러 단어로 부르지 않는다. 통계·개발 용어는 화면에 내지 않는다.

| 개념 | 쓰는 말 | 쓰지 않는 말 |
| --- | --- | --- |
| 모이는 날 하나 | **일정** (순서를 셀 때만 "회차") | 모임, 활동 |
| 팀에 속한 사람 | **팀원** | 회원, 선수, 플레이어 |
| 계정 없이 온 사람 | **게스트** | 손님, 비회원 |
| 그날 오기로 한 사람 | **참석자** | 참가자 |
| 팀을 나누는 일 | **팀 배정**, 결과 하나는 **배정안** | 편성, 후보안, 팀 짜기, 실행 |
| 경기 기록 화면 | **경기 기록** | 쿼터 기록 |
| 실력 표시 | 모두에게 **실력 등급**(A~E), 매니저에게 **실력 점수** | 지표, 티어, 실력값, 종합 실력 |
| 실력의 근거 | **시작 점수**, **기여 점수**, **점수 차**, **정보 충분도**, **세부 능력** | 사전값, 잔차, 코트 마진, 신뢰도, 6축 |
| 참석 여부 | **참석 응답** | RSVP |
| 경기 후 평가 | **투표** | 피어 설문, 응답 |
| 배정 조건 | **묶기 / 갈라놓기 / 미리 배치** | 제약, LOCK/SEPARATE/PIN |

문체는 화면·서버 메시지 모두 **해요체**로 통일한다. 보조용언은 띄어 쓴다("골라 주세요"). 서버가 주는 오류 문구도 그대로 화면에 뜨므로 같은 규칙을 지키고, 컬럼명·HTTP 메서드·환경 변수 이름·내부 id 는 담지 않는다.

## 3. 화면별 요소 · 데이터 · API · 흐름

### S-01 로그인
- **UI 요소:** HOOPLY 로고·문구, 카카오로 시작하기(노란 버튼), 이메일·비밀번호 입력, 로그인 버튼, 회원가입 링크
- **데이터 필드:** `email`, `password` → 응답 `access_token`, `refresh_token`
- **API:** `POST /auth/login`, `GET /auth/kakao/login-url?redirect_uri=` (카카오 버튼)
- **흐름:** 성공 → 홈. 카카오 버튼은 인가 URL로 이동(state를 sessionStorage에 보관). 401 → "이메일 또는 비밀번호가 올바르지 않습니다."

### S-02 회원가입
- **UI:** 이메일, 비밀번호(8자 이상), 이름, 닉네임(선택), 키(cm), 가입 버튼
- **필드:** `SignupRequest{email, password, name, nickname?, height_cm?}` → `TokenPair`
- **API:** `POST /auth/signup`
- **흐름:** 성공 → S-03 설문. `409 EMAIL_DUPLICATED` → 필드 오류 표시.

### S-03 온보딩 설문
- **UI:** 진행률, 문항 카드(단일선택은 자동 다음, 다중선택 칩, 5단계 서열, 키 스테퍼), 이전/다음, 제출
- **필드:** `SurveyTemplate{id, questions[]{id, code, answer_type, options[]}}` → `SurveyResponseIn{template_id, answers[]{question_id, option_ids[] | numeric_value}}` → `MyProfile`
- **API:** `GET /surveys/onboarding`, `POST /surveys/onboarding/responses`
- **흐름:** 제출 → 팀 코드가 있으면 S-06, 없으면 홈. 재제출은 `409 ALREADY_SUBMITTED`.

### S-04 홈
- **UI:** 인사말, 다음 모임 카드(D-day·일시·내 응답 상태), 게스트 기록 확인 카드(같은 이름의 미병합 게스트가 있을 때), 다가오는 일정 목록, 내 팀 목록(기본 팀 배지·"기본 팀으로 설정하기"), 팀 코드로 가입·팀 만들기 버튼, 하단 탭(홈/프로필)
- **필드:** `UserDetail{name, nickname, onboarding_completed, primary_team_id}`, `TeamMembershipView{team_id, team_name, team_status, approval_status, role, member_count}`, `EventView{event_date, start_time, venue, my_attendance, attend_count}`
- **API:** `GET /me`, `GET /me/teams`, `GET /teams/{id}/events?size=50` (팀별), `PATCH /me{primary_team_id}`
- **흐름:** 설문 미완료면 설문 유도 카드가 먼저. 일정 카드 탭 → S-10. 팀 카드 탭 → S-07.

### S-05 팀 생성
- **UI:** 팀 이름, 소개, 홈 코트, 발급 버튼 → 완료 화면(팀 코드, 복사, 카카오톡 공유, 승인 대기 안내)
- **필드:** `TeamCreate{name, description?, home_court?}` → `TeamCreated{id, team_code}`
- **API:** `POST /teams`
- **흐름:** 생성 → 승인 대기(관리자 콘솔) → 5명 이상 → 활성. 공유 문구에 초대 링크 `/teams/join?code=`.

### S-06 팀 가입
- **UI:** 8자리 코드 입력(초대 링크면 미리 채움), 가입 버튼
- **필드:** `{team_code}` → `TeamDetail`
- **API:** `POST /teams/join`
- **흐름:** 성공 → S-23 내 위치 설정 → 팀 상세. `404 TEAM_CODE_NOT_FOUND` 인라인 오류, `409 ALREADY_MEMBER` 안내 후 이동.

### S-07 팀 상세
- **UI:** 헤더(회원 수·홈 코트·상태 배지·승인 대기 배너·팀 코드 복사/공유), 탭(일정 | 기록 | 팀원). 일정 탭: 일정 등록(매니저), 투표 배너(끝난 일정·미투표), 예정 일정 → 지난 일정(흐리게) 5개씩 페이지, 확정 배정 대시보드(팀 블랙/화이트·균형 점수). 기록 탭: S-25. 팀원 탭: 팀원 카드(등급은 매니저만)
- **첫 탭:** 평소엔 일정. 달이 바뀐 뒤 처음 열면 딱 한 번 기록 탭이 먼저 열린다(지난달 월간 랭킹이 확정됐다는 뜻). "지난 방문 달"을 기기(localStorage)에 기억한다
- **필드:** `TeamDetail{name, status, approval_status, team_code, member_count, my_role, my_player_id}`, `EventView{…, survey_open, my_survey_submitted, adopted_candidate_id}`, `AdoptedAssignment{squads[]{squad_name, members[]{display_name, kind}, assigned_positions}, total_score, my_player_id}`, `PlayerCard[]`
- **API:** `GET /teams/{id}`, `GET /teams/{id}/events`, `GET /events/{id}/assignment/adopted`, `GET /teams/{id}/players`
- **흐름:** 우측 상단 "팀 관리" → S-08(매니저). 투표 배너 → S-16.

### S-08 팀 관리 (MANAGER)
- **UI:** 팀 이름/소개 수정 카드, 팀 코드 재발급, 실력 정렬 카드, 지난 기록 추가 카드, 정렬 칩(실력/포지션/참여 ▼▲), 회원 행(이름·팀장/매니저 배지·포지션·실력 수치·참여 횟수·등급·⋯ 메뉴: 지표 보기 / 매니저 지정·해제(팀장만) / 팀에서 제외), 기록 이어받기 제안(게스트→회원 병합)
- **필드:** `PlayerCardDetailed{display_name, role, user_id, primary_position, skill_grade, skill_overall, prior_overall, attended_events, quarters_played}`, `TeamDetail.owner.id`, `MergeCandidate{guest, member}`
- **API:** `PATCH /teams/{id}`, `POST /teams/{id}/code:regenerate`, `GET /teams/{id}/players?sort=skill`, `PATCH /teams/{id}/players/{pid}/role`, `DELETE /teams/{id}/players/{pid}`, `GET /teams/{id}/guests/merge-candidates`, `POST /players/{gid}:merge`
- **흐름:** 본인 해제는 팀장 승계 확인 팝업 → 성공 시 팀 화면으로. 마지막 매니저 해제·제외는 `422 CANNOT_DEMOTE_LAST_MANAGER`.

### S-09 일정 등록
- **UI:** "최근 일정과 같게 채우기" 카드(불러올 일정의 제목·일시·장소·메모를 보여주고, 채우면 카드가 사라지고 안내 한 줄만 남음. 날짜·응답 마감은 +7일이며 입력만 채우고 저장하지 않음), 제목, 날짜, 시작/종료(시작을 바꾸면 종료가 같은 진행 시간만큼 따라옴 — 기본 2시간, 종료를 직접 고치거나 지난 일정을 채우면 그 길이를 유지), 장소, 응답 마감(날짜+시각 2칸, 날짜만 고르면 22:00), 메모, 등록 버튼
- **필드:** `EventCreate{title?, event_date, start_time?, end_time?, venue?, rsvp_deadline?, memo?}` → `EventView`
- **API:** `POST /teams/{id}/events`
- **흐름:** 팀이 비활성이면 `422 TEAM_NOT_ACTIVE`(승인 전/5명 미만 문구 구분).

### S-10 일정 상세 · 참석 응답
- **UI:** 헤더(일시·장소·상태 배지·참석 수), [끝난 일정·매니저] 경기 기록 버튼과 투표 현황·독려 공유 카드가 맨 위, 참석/불참 토글, 응답 미리 마감(매니저), 게스트 초대 버튼(응답 열려 있을 때), 참석 요약(참석/미응답/불참·포지션 분포·경고), 배정 확정 결과 버튼, 팀 배정하러 가기(매니저, 10명 이상), 참석자 그룹 목록(접기)
- **필드:** `EventView{status, rsvp_open, my_attendance, attend_count, adopted_candidate_id, quarter_count, survey_open, survey_responded, survey_total, my_survey_submitted, start_time}`, `AttendanceList{items[]{player, status, registered_by_name, team_lock_request_player_name}, summary{attend, pending, absent, position_counts, warnings}}`
- **API:** `GET /events/{id}`, `PUT /events/{id}/attendance`, `POST /events/{id}/rsvp:close`, `GET /events/{id}/attendances`, `PUT /events/{id}/attendances/{pid}`, `DELETE /events/{id}`, `GET /events/{id}/post-game-survey/share-message`
- **흐름:** 마감·종료면 토글 비활성 + "응답 기한이 지난 일정이에요". 쿼터 기록 버튼은 시작 시각 이후에만.

### S-11 참석자 현황 · 게스트 초대 시트
- **UI:** 이전에 초대한 사람 불러오기 칩, 이름, 키, 대략적 실력 1~5, 선호 포지션(가능 포지션에 자동 포함), 가능 포지션 칩, "나와 같은 팀으로 묶어주세요", 동명이인 확인 목록(같은 사람 / 새 게스트로 추가)
- **필드:** `EventGuestCreate{display_name, height_cm?, skill_grade?, preferred_position?, playable_positions[], team_lock_request, existing_player_id?, force_new?}` → `AttendanceView` 또는 `GuestSimilar{similar[]}`, `GuestPresetView{display_name, skill_grade, height_cm, …, existing_player_id}`
- **API:** `POST /events/{id}/guests`, `PATCH/DELETE /events/{id}/guests/{pid}`, `GET /events/{id}/guests/presets`
- **흐름:** 동명이인이면 201 대신 200 `similar[]` → 선택 후 재요청.

### S-12 팀 배정 실행 (MANAGER)

- **API:** `GET /players/{pid}/stats`, `GET /teams/{id}/stats/monthly-margin?period=YYYY-MM`, `GET /teams/{id}/stats/periods`, `GET /me/badges`
- **왜 코트 마진인가:** 실력 지표(잔차)는 매니저만 보지만, 코트 마진은 "그 달 코트에서 벌어진 결과"라 전원이 봐도 된다. 다만 팀이 하루 고정이라 이긴 팀 6~7명이 비슷한 값을 받으므로 화면 문구에서 "실력"이라 부르지 않는다. 순위는 합계가 아니라 **쿼터당 평균**이고, 그 달 팀 전체 쿼터의 30%(`margin_rank_min_share`) 미만 출전자는 순위에서 뺀다 — 2쿼터 뛰고 +12인 사람이 1등이 되지 않게
- **새 달 첫 방문:** 랭킹이 접혀 있어도 펼쳐 보여 주고, 달 드롭다운을 지난달로 맞춘 뒤 "새 달이 시작됐어요. 9월 최종 순위예요" 안내를 붙인다

### S-27 시작 안내 (튜토리얼)
- **목표:** 처음 쓰는 사람이 팀에 들어가 첫 경기를 준비하게 돕되, 억지로 따라가게 하지 않는다. 가짜 화면은 만들지 않는다
- **① 시작 팝업 (한 번):** 새 가입자가 홈에 처음 오면 "처음이시죠?" 팝업. **안내 받기** / **혼자 둘러볼게요**. 거절하면 체크리스트도 기능별 첫 안내도 뜨지 않는다. 가입 직후 설문으로 바로 보내던 것은 홈으로 바꿨다
- **② 홈 체크리스트:** 경로를 먼저 고른다("팀 코드를 받으셨나요?"). 며칠 안에 끝나는 준비 4단계만 담는다

  | | 팀원 | 매니저 |
  | --- | --- | --- |
  | 1 | 팀 코드로 가입 | 팀 만들기 |
  | 2 | 실력·포지션 설문 | 실력·포지션 설문 |
  | 3 | 이 동호회에서 내 실력 위치 | 팀원 초대 (팀 활성화까지 · 승인 상태와 n/5명) |
  | 4 | 첫 일정에 참석 응답 (본인 응답만) | 첫 일정 등록 |

  단계는 **서버가 실제 데이터로 판정**한다(`GET /me/tutorial`). 다른 사람의 행동이 먼저 필요한 단계는 숨기지 않고 **대기 중** + 이유("매니저가 일정을 올리면 여기서 바로 응답할 수 있어요", "팀이 활성화되면 열려요")로 보여 주고, 조건이 채워지면 저절로 누를 수 있게 바뀐다. × 로 닫으면 끝. 다 마치면 "앞으로 이런 순서로 진행돼요" 흐름표를 한 번 보여 주고 사라진다. 체크리스트가 떠 있는 동안 홈의 "설문 아직" 카드는 숨긴다
- **②-1 스포트라이트:** 안내 중에는 지금 할 칸만 밝게 두고 나머지 화면을 어둡게 덮는다(칸에 주황 테두리 + 짧은 말풍선). 홈에서는 경로 선택 칸 → 다음 할 일 칸을 한 번씩 밝히고(같은 단계는 한 번만, 기기에 기억), 단계 버튼을 눌러 들어간 화면에서는 그 화면의 할 칸을 밝힌다 — 팀 코드 입력칸과 가입하기 · 팀 이름과 팀 코드 발급받기 · 팀 코드 공유 칸 · 참석/불참 버튼 · 날짜와 등록 버튼. 설문과 내 위치 문항은 화면 전체가 그 일이라 밝히지 않는다. 덮개는 누르는 것을 막지 않고, 밝은 칸을 누르거나 "알겠어요"·Esc 로 사라진다. 대상 칸은 `data-tutorial="<단계 키>"` 로 표시하고 말풍선 문장은 `tutorial-content.ts` 의 `SPOTLIGHT`
- **③ 기능별 첫 안내:** 배정·경기 기록·투표·배정 결과·기록 탭은 경기가 있어야 열려서 체크리스트에 넣지 않는다. 대신 그 화면에 **처음 들어갔을 때** 맨 위에 닫을 수 있는 안내 한 장(도움말 해당 주제 링크 + "알겠어요"). 닫은 안내는 다시 뜨지 않는다
- **상태:** `users.tutorial_state`(PENDING · ACTIVE · CLOSED · DONE · DECLINED) · `tutorial_path` · `tutorial_tips_seen`. 기능 도입 전 가입자는 DECLINED — 아무것도 뜨지 않는다. 도움말 맨 위 "시작 안내 다시 보기"로 누구나 다시 켤 수 있다(경로 선택부터)
- **문장:** `frontend/src/lib/tutorial-content.ts` (첫 안내 · 흐름표), 단계 문구는 `backend/app/services/tutorial_service.py`

- **카카오톡 안 브라우저:** 메일 링크가 동작하지 않을 수 있어 주소 복사를 주 수단으로 둔다

### S-21 팀 리더보드
- **UI:** 탭(참여율 / 출전 쿼터 / 기여 점수(매니저)), 기간 드롭다운(전체 · "2026년 8월"), 순위 목록. 진입은 S-25 기록 탭의 "리더보드 더 보기"
- **필드:** `LeaderboardEntry{rank, player, value, detail}`, 기간 목록 `{items: ["2026-09", "2026-08"]}`
- **API:** `GET /teams/{id}/stats/leaderboard?metric=&period=`, `GET /teams/{id}/stats/periods`
- **기간:** 드롭다운에는 **기록이 있는 달만** 들어간다. 취소되지 않은 지난 일정이 있는 달을 서버가
  최신순으로 내려 주므로, 빈 달을 골라 놓고 아무것도 안 나오는 상황이 생기지 않는다.
- **세 지표 모두 기간으로 좁힌다.** 기여 점수는 프로필의 누적 총합이 아니라 그 기간 쿼터에 남긴 몫의
  합이다(`quarter_lineups.residual`). 총합을 쓰면 어느 달을 골라도 같은 값이 나온다.
- **정렬:** 그 기간에 기록이 없는 사람은 맨 아래("출전 없음"). 0 을 성적으로 치면 못한 사람이
  안 나온 사람보다 아래로 밀린다. 병합된 게스트의 기록은 회원 쪽으로 합산한다.

### S-22 지난 기록 추가 (MANAGER)
- **UI:** 1단계 날짜·시간·장소 → 2단계 회원 체크, 게스트 이름·키 추가(동명이인 확인) → 쿼터 기록(S-15)으로 이동
- **API:** `POST /teams/{id}/events`, `PUT /events/{id}/attendances/{pid}`, `POST /events/{id}/guests`, 이후 S-15
- **흐름:** 참석 10명 미만이면 다음 단계 잠금.

### S-23 동호회 내 내 위치
- **UI:** 팀 이름, 5단계(상위 10% … 하위 10%) 선택, 저장
- **API:** `PUT /teams/{id}/self-rank`
- **흐름:** 팀 가입 직후 자동 진입, 프로필에서 수정 가능. 저장 → 진입한 화면으로 복귀.

### S-24 카카오 로그인 콜백
- **UI:** 로고 + "카카오 계정을 확인하고 있어요…", 실패 시 오류와 로그인 화면 버튼
- **필드:** 쿼리 `code`, `state` → `KakaoTokenPair{access_token, refresh_token, is_new}`
- **API:** `GET /auth/kakao/callback?code&state&redirect_uri`, 연결 모드면 `POST /auth/kakao/link`
- **흐름:** sessionStorage의 state와 대조 → 신규면 S-03, 기존이면 홈, 연결 모드면 S-17.

## 4. 사용자 흐름

**흐름 A — 신규 플레이어 온보딩**
S-01 → (카카오 또는 S-02 가입) → S-03 설문 → 팀 코드 있음? 예: S-06 → S-23 내 위치 → S-07 / 아니오: S-05 팀 생성 → 코드 공유 → 관리자 승인 대기

**흐름 B — 모임 운영 (매니저)**
S-09 일정 등록 → (응답 수집, 게스트 초대 S-11) → S-10 참석 현황 → (필요 시 응답 미리 마감) → S-12 배정 실행(제약 설정) → S-13 후보안 비교·수정 → 확정(S-14 공개) → 일정 시작 후 S-15 쿼터 기록 → 일정 종료 후 S-10에서 투표 독려 공유

**흐름 C — 참여 (플레이어)**
S-04 홈 다음 모임 카드 → S-10 참석 응답 → (확정 후) S-14 결과 → 일정 종료 후 S-07 투표 배너 → S-16 투표 → S-17 기록 확인

**흐름 D — 게스트가 회원이 된 경우**
게스트로 S-11 등록·기록 누적 → 본인이 S-02/카카오 가입 + S-06 팀 가입 → 홈(S-04)·팀(S-07)에 "이전 모임 기록이 있어요. 본인이 맞나요?" 카드 → **내 기록이에요**(병합) / **아니에요**(다시 묻지 않음). 이름이 다르면 S-08 "기록 이어받기 제안"으로 매니저가 병합

## 5. 예외 · 오류 시나리오

| 시나리오 | 조건 | 화면 처리 | API 응답 |
| --- | --- | --- | --- |
| 잘못된 팀 코드 | 없는/만료 코드 | 입력 필드 인라인 오류 | `404 TEAM_CODE_NOT_FOUND` |
| 중복 가입 | 이미 소속 | 안내 후 팀 상세 이동 | `409 ALREADY_MEMBER` |
| 팀 미활성 | 승인 전 또는 5명 미만 | 일정 등록 버튼 비활성 + 사유 문구 | `422 TEAM_NOT_ACTIVE` |
| 카카오 계정에 이메일 없음 | 동의항목 미제공 | 이메일 없이 가입, 프로필에 "이메일 없음" | `201` + `email: null` |
| 카카오 인증 실패 | state 불일치·토큰 교환 실패 | 콜백 화면 오류 + 로그인 화면 버튼 | `401 KAKAO_AUTH_FAILED` |
| 게스트 동명이인 | 같은 이름 게스트 존재 | 기존 목록 먼저 보여주고 "새 게스트로 추가" | `200 similar[]` |
| 게스트 데이터 없음 | 등급 미지정 | 칩에 `?` 배지, 설명에 "클럽 평균으로 계산" | `skill_confidence = 0` |
| 인원 부족 배정 | 참석 < 10 | 실행 버튼 비활성 + "10명 이상 필요 · 현재 N명" | `422 NOT_ENOUGH_PLAYERS` |
| 고르게 나눌 수 없는 묶음 | 묶음 크기 때문에 8:8(홀수면 9:8)이 불가능 | 차단하지 않고 9:7 → 10:6 순으로 인원을 벌려 나눈 뒤 "두 팀 인원을 9:7로 나눴어요" 경고 | `200` + `warnings[]` |
| 묶음 과대·분할 불가·충돌 | 한 팀이 되면 상대 팀이 5명 미만 · 어떻게 나눠도 양 팀 5명 이상이 안 됨 · 충돌 | 실행 전 인라인 경고 + 문제 인원 표시 | `422 LOCK_GROUP_TOO_LARGE / LOCK_PARTITION_INFEASIBLE / CONSTRAINT_CONFLICT / SEPARATE_INFEASIBLE / SQUAD_OVERFLOW` |
| 빅맨·핸들러 부족 | 4·5번 또는 1번 가능자 < 팀 수 | 경고 배너(차단 아님) | `200` + `warnings[]` |
| 잘못된 교체 | 팀 최소 5명 미만, 갈라놓은 쌍 한 명만 이동 | 버튼 잠금 + 사유 | `422 INVALID_SWAP` |
| 응답 마감 후 응답 | 마감 시각·미리 마감 | 토글 비활성 + "응답 기한이 지난 일정이에요" | `422 RSVP_CLOSED` |
